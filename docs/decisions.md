# Decisions

Tool and architecture choices, in the order they were made. Open source first.

| # | Decision | Chosen | Why / alternatives |
|---|---|---|---|
| 1 | First scope | Consents (3.3.1) + Accounts (2.4.2) | Phase 2 data sharing: consent lifecycle and cross-endpoint consistency. Phase 1 open data was simpler but has no consent or security. Accounts 2.5.0 is still beta. |
| 2 | Transformations | PySpark on Kubernetes | Replaces dbt (used in payer-data-readiness); closer to production data platforms. |
| 3 | Table format | Apache Iceberg 1.12.0 | Engine-neutral; Delta was the alternative. |
| 4 | Iceberg catalog | JDBC catalog in Postgres (CloudNativePG) | Safe for concurrent commits with one small service. REST catalog (Lakekeeper, Polaris) is closer to production but one more service; the Hadoop catalog on S3 is unsafe for concurrent writes. |
| 5 | Object store | SeaweedFS 4.54 (all-in-one, S3 gateway) | Apache 2.0 and active. MinIO's repository was archived (last release 2025-10-15). Garage is AGPL; Ceph RGW too heavy for kind/CI. |
| 6 | Spark | 3.5.9 (Scala 2.12, Java 17) | Long-lived line, most common in production. |
| 7 | Local Kubernetes | kind v0.33.0 (node v1.37.0) | Runs the same way on a laptop and on GitHub runners. |
| 8 | Installs | Helm charts with pinned versions and values files | CloudNativePG 0.29.1, SeaweedFS 4.54.0, Spark Operator 2.6.0. |
| 9 | Mock transmitter | ~~Same approach as the official [mock-api](https://github.com/OpenBanking-Brasil/mock-api): [openapi-mock](https://github.com/muonsoft/openapi-mock) on the official specs, plus a defect proxy~~ Replaced by 13 | The official images cover Phase 1 only and are frozen at v1.0.0-rc5.3 (2024). |
| 10 | Pinning the specifications | Downloaded from [OpenBanking-Brasil/openapi](https://github.com/OpenBanking-Brasil/openapi) at a fixed commit, checked by SHA-256 (`make specs`) | The upstream repository declares no license, so the files are not redistributed here. Vendoring them was the alternative (offline, visible diffs). |
| 11 | Spec linter | Spectral 6.17.0, Docker image pinned by digest | No Node.js on the host or in CI. 6.17.1 was ten days old when chosen. |
| 12 | Lint ruleset and failure policy | `spectral:oas` (recommended) plus `ofb-*` rules for the conventions every pinned operation follows; fail on errors only | Warnings are reported and the known ones listed in [spec-findings.md](spec-findings.md). Each `ofb-*` rule must fire on a defective fixture, so a rule that silently matches nothing fails CI. |
| 13 | Mock transmitter (revises 9) | Own synthetic transmitter (Python, FastAPI) over a seeded dataset, with consent state; defects injected by a separate proxy of our own (item 2b) | openapi-mock 0.3.9 on the pinned specs returned random data on every call, no state, no `x-fapi-interaction-id` header and out-of-spec values (year 3202, currency `QSN`): the clean baseline would already be defective and business rules would have nothing coherent to check. See [transmitter.md](transmitter.md). |
| 14 | Python dependencies | uv 0.13.6 with `uv.lock` (resolution limited to packages at least two weeks old); images on `python:3.13-slim-bookworm` pinned by digest | pip-tools with hashed requirements was the alternative: standard tools, slower and more verbose. |
| 15 | Response validation | openapi-core 0.23 | Validates status, headers, content type and body (with `$ref`, `pattern`, `format`) against OpenAPI 3.0. Alternatives: plain jsonschema on extracted schemas (reimplements the rest), Schemathesis already in item 2 (mixes items 2 and 3). |
| 16 | Defect catalogue | 8 classes. Contract: missing required field, invalid format, missing `x-fapi-interaction-id`, undeclared field. Business: inconsistent balance, broken pagination, consent not enforced, transaction outside the window | Business defects keep the response valid against the spec, so each layer is measured on its own. `undeclared-field` measures what schema validation cannot see. The four classes of the original backlog and a 10-class version were the alternatives. See [defects.md](defects.md). |
| 17 | Defect selection | Deterministic: SHA-256 of seed, method, path, sorted query and consent; per-class rates; at most one defect per response | Reproducible regardless of call order or concurrency, and the validators cannot steer it. A seeded random sequence breaks under parallel calls; a fixed campaign has no rate and can be learned. |
| 18 | Labels (ground truth) | JSONL for every exchange, clean included, in `s3://lakehouse/labels/run=<id>/`, written with boto3 | Precision needs the negatives. The same JSONL-in-S3 shape as the validator results (item 3); Spark reads both. Writing to Iceberg from the proxy (pyiceberg) would tie it to the catalog and to concurrent commits. |
| 19 | Contract validator | Own validator on openapi-core 0.23 (already used by the tests), walking the seeded resources through the proxy | The layer must check real traffic through the proxy and be joined with its labels. Schemathesis (in the original backlog) generates its own requests (property-based), which fits fuzzing better than checking a fixed walk. It also adds dependencies and would need hooks for the rules below. It can come back later as a separate fuzzing job. See [validator.md](validator.md). |
| 20 | Contract rules beyond the schema | `interaction-id.echo` (error) and `strict.undeclared-field` (warning), next to the `schema.*` rules | Without them, `missing-interaction-id` on Consents and on Accounts errors, and `undeclared-field` everywhere, are invisible to the contract layer ([spec-findings.md](spec-findings.md)). The severity separates what the specs require from what they only leave undocumented. |
| 21 | Validator output | JSONL in `s3://lakehouse/contract/run=<id>/` (results) and `exchanges/run=<id>/` (request and response), under the proxy's run id, parts named by walk id | Same shape and key as the labels (decision 18), so item 5 joins them on `interaction_id`. The exchange log is what the business-rules job (item 4) reads. Bodies are kept as text, so each route can be parsed with its own schema. |
| 22 | Reading JSONL from S3 in Spark | S3A connector: hadoop-aws 3.3.4 (the image's Hadoop) with aws-java-sdk-bundle 1.12.262, pinned by SHA-256 | Distributed reads, as a production job would do. The SDK bundle adds about 280 MB to the Spark image. Reading the objects with boto3 in the driver does not scale. Having the validator write Iceberg directly contradicts decision 18. |
| 23 | Business rules | One rule per business defect class (balance, pagination with three variants, consent enforcement, booking window). The walk reads each consent before using it and probes the next page after a full page with no next link | Each class is measured by the rule meant for it. General invariants (unique ids, `transactions-current` within `transactions`, check digits) are left for later. Without the consent reads the job cannot know a consent's state. Without the probe a dropped `next` on a page-by-page listing cannot be told from the last page. See [business-rules.md](business-rules.md). |
| 24 | Business layer and contract failures | Only 2xx exchanges with contract verdict `pass` or `warn` are parsed; rules whose inputs are missing say `inconclusive` | The layers stay separate, as in a gated pipeline. Running on everything would count contract defects as business findings. The price: under the default rates many balance and consent checks are inconclusive, which item 5 should report. |
| 25 | Business tables | Iceberg `lake.ofb`: bronze (`exchanges`, `contract_results`), silver (`consent_reads`, `balances`, `listing_pages`, `listing_items`), gold (`business_checks` with `pass`/`finding`/`inconclusive`), partitioned by `run_id`, `overwritePartitions` | Reruns replace their partition. The silver tables serve the later items. A single findings table was the alternative. Recording passes and inconclusive checks gives item 5 the denominators. |
| 26 | Business job tests | pytest with a local PySpark 3.5.9 on Python 3.10 (the image's), over runs exported in process by the validator's harness; plus an in-cluster smoke that compares the checks with the labels | Fast feedback without a cluster. The transmitter, proxy and validator need Python 3.13, so they export the runs as files rather than sharing one environment. Testing only in the cluster was the alternative. |
| 27 | Detection report | PySpark job (`jobs/report`) over the Iceberg tables and the labels (kept as bronze `labels`); gold `detection_*` tables partitioned by report name, plus Markdown in `s3a://lakehouse/reports/` | Same platform as item 4, and the history of reports can be queried. A standalone script was the alternative: no history. So were SQL views over Iceberg: hard to test, no readable report. See [report.md](report.md). |
| 28 | Metrics | The unit is the exchange. Recall per class, strict (inconclusive = missed) and conditional (over conclusive); precision per rule against its target classes and per layer; class × rule matrix; 95 % Wilson intervals | Precision per class is undefined when a rule serves two classes (`schema.body`). Strict and conditional recall separate the cost of the gating from the quality of the rules. With 1 to 10 positives per class, a bare percentage would mislead. |
| 29 | Volume | Campaigns: `make campaign` runs one validation per defect seed with more customers and reports them together; CI keeps one small run. The walk also fetches each history in one page of 1000 | More data where it matters (the committed report) without slowing CI. The single-page history cut the inconclusive balances from 7 of 9 to 3 of 9. |
| 30 | Gate | The report fails on the catalogue's invariants (precision 1 in both layers, conditional recall 1, no inconclusive contract check); strict business recall is reported, not gated. It replaces the business job's `--verify-labels` | One place compares with the ground truth. Strict recall varies with the seed and the day, so a threshold on it would be flaky. |
| 31 | More positives for the rare classes | The transmitter seeds the non-happy consents (expired, revoked, without balances, awaiting) for every customer, and the walk uses them on the accounts list and every balance. Per customer, `BALANCE_CONSENTS` (2) new consents read every balance again. The balance rule takes the account's history from any consent of the walk | In v1.0.0's reference campaign, `consent-not-enforced` had 3 positives and `inconsistent-balance` 10. Repeating a request does not help, because the draw depends on the request. A focused campaign with boosted rates was the alternative; it is left for later, as a separate report. The proxy needs no change. |
| 32 | Path dependencies between services | `editable = true` for the transmitter and the proxy in the test environments of the proxy and the validator | A non-editable path dependency is built once and is not rebuilt when its code changes, so local tests can run against stale code. CI always starts from a fresh environment. |
