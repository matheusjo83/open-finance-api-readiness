# Decisions

Tool and architecture choices, in the order they were made. Open source first.

| # | Decision | Chosen | Why / alternatives |
|---|---|---|---|
| 1 | First scope | Consents (3.3.1) + Accounts (2.4.2) | Phase 2 data sharing: consent lifecycle and cross-endpoint consistency. Phase 1 open data was simpler but has no consent or security. Accounts 2.5.0 is still beta. |
| 2 | Transformations | PySpark on Kubernetes | Replaces dbt (used in payer-data-readiness); closer to production data platforms. |
| 3 | Table format | Apache Iceberg 1.12.0 | Engine-neutral; Delta was the alternative. |
| 4 | Iceberg catalog | JDBC catalog in Postgres (CloudNativePG) | Safe for concurrent commits with one small service. REST catalog (Lakekeeper, Polaris) is closer to production but one more service; the Hadoop catalog on S3 is unsafe for concurrent writes. |
| 5 | Object store | SeaweedFS 4.54 (all-in-one, S3 gateway) | Apache 2.0 and active. MinIO's repository was archived (last release 2025-10-15). Garage is AGPL; Ceph RGW too heavy for kind/CI. |
| 6 | Spark | 3.5.9 (Scala 2.12, Java 17) | Long-lived line, most common in production. |
| 7 | Local Kubernetes | kind v0.33.0 (node v1.37.0) | Runs the same way on a laptop and on GitHub runners. |
| 8 | Installs | Helm charts with pinned versions and values files | CloudNativePG 0.29.1, SeaweedFS 4.54.0, Spark Operator 2.6.0. |
| 9 | Mock transmitter | ~~Same approach as the official [mock-api](https://github.com/OpenBanking-Brasil/mock-api): [openapi-mock](https://github.com/muonsoft/openapi-mock) on the official specs, plus a defect proxy~~ Replaced by 13 | The official images cover Phase 1 only and are frozen at v1.0.0-rc5.3 (2024). |
| 10 | Pinning the specifications | Downloaded from [OpenBanking-Brasil/openapi](https://github.com/OpenBanking-Brasil/openapi) at a fixed commit, checked by SHA-256 (`make specs`) | The upstream repository declares no license, so the files are not redistributed here. Vendoring them was the alternative (offline, visible diffs). |
| 11 | Spec linter | Spectral 6.17.0, Docker image pinned by digest | No Node.js on the host or in CI. 6.17.1 was ten days old when chosen. |
| 12 | Lint ruleset and failure policy | `spectral:oas` (recommended) plus `ofb-*` rules for the conventions every pinned operation follows; fail on errors only | Warnings are reported and the known ones listed in [spec-findings.md](spec-findings.md). Each `ofb-*` rule must fire on a defective fixture, so a rule that silently matches nothing fails CI. |
| 13 | Mock transmitter (revises 9) | Own synthetic transmitter (Python, FastAPI) over a seeded dataset, with consent state; defects injected by a separate proxy of our own (item 2b) | openapi-mock 0.3.9 on the pinned specs returned random data on every call, no state, no `x-fapi-interaction-id` header and out-of-spec values (year 3202, currency `QSN`): the clean baseline would already be defective and business rules would have nothing coherent to check. See [transmitter.md](transmitter.md). |
| 14 | Python dependencies | uv 0.13.6 with `uv.lock` (resolution limited to packages at least two weeks old); images on `python:3.13-slim-bookworm` pinned by digest | pip-tools with hashed requirements was the alternative: standard tools, slower and more verbose. |
| 15 | Response validation | openapi-core 0.23 | Validates status, headers, content type and body (with `$ref`, `pattern`, `format`) against OpenAPI 3.0. Alternatives: plain jsonschema on extracted schemas (reimplements the rest), Schemathesis already in item 2 (mixes items 2 and 3). |
| 16 | Defect catalogue | 8 classes. Contract: missing required field, invalid format, missing `x-fapi-interaction-id`, undeclared field. Business: inconsistent balance, broken pagination, consent not enforced, transaction outside the window | Business defects keep the response valid against the spec, so each layer is measured on its own. `undeclared-field` measures what schema validation cannot see. The four classes of the original backlog and a 10-class version were the alternatives. See [defects.md](defects.md). |
| 17 | Defect selection | Deterministic: SHA-256 of seed, method, path, sorted query and consent; per-class rates; at most one defect per response | Reproducible regardless of call order or concurrency, and the validators cannot steer it. A seeded random sequence breaks under parallel calls; a fixed campaign has no rate and can be learned. |
| 18 | Labels (ground truth) | JSONL for every exchange, clean included, in `s3://lakehouse/labels/run=<id>/`, written with boto3 | Precision needs the negatives. The same JSONL-in-S3 shape as the validator results (item 3); Spark reads both. Writing to Iceberg from the proxy (pyiceberg) would tie it to the catalog and to concurrent commits. |
| 19 | Contract validator | Own validator on openapi-core 0.23 (already used by the tests), walking the seeded resources through the proxy | The layer must check real traffic through the proxy and be joined with its labels. Schemathesis (in the original backlog) generates its own requests (property-based), which fits fuzzing better than checking a fixed walk. It also adds dependencies and would need hooks for the rules below. It can come back later as a separate fuzzing job. See [validator.md](validator.md). |
| 20 | Contract rules beyond the schema | `interaction-id.echo` (error) and `strict.undeclared-field` (warning), next to the `schema.*` rules | Without them, `missing-interaction-id` on Consents and on Accounts errors, and `undeclared-field` everywhere, are invisible to the contract layer ([spec-findings.md](spec-findings.md)). The severity separates what the specs require from what they only leave undocumented. |
| 21 | Validator output | JSONL in `s3://lakehouse/contract/run=<id>/` (results) and `exchanges/run=<id>/` (request and response), under the proxy's run id, parts named by walk id | Same shape and key as the labels (decision 18), so item 5 joins them on `interaction_id`. The exchange log is what the business-rules job (item 4) reads. Bodies are kept as text, so each route can be parsed with its own schema. |
| 22 | Reading JSONL from S3 in Spark | S3A connector: hadoop-aws 3.3.4 (the image's Hadoop) with aws-java-sdk-bundle 1.12.262, pinned by SHA-256 | Distributed reads, as a production job would do. The SDK bundle adds about 280 MB to the Spark image. Reading the objects with boto3 in the driver does not scale. Having the validator write Iceberg directly contradicts decision 18. |
| 23 | Business rules | One rule per business defect class (balance, pagination with three variants, consent enforcement, booking window). The walk reads each consent before using it and probes the next page after a full page with no next link | Each class is measured by the rule meant for it. General invariants (unique ids, `transactions-current` within `transactions`, check digits) are left for later. Without the consent reads the job cannot know a consent's state. Without the probe a dropped `next` on a page-by-page listing cannot be told from the last page. See [business-rules.md](business-rules.md). |
| 24 | Business layer and contract failures | Only 2xx exchanges with contract verdict `pass` or `warn` are parsed; rules whose inputs are missing say `inconclusive` | The layers stay separate, as in a gated pipeline. Running on everything would count contract defects as business findings. The price: under the default rates many balance and consent checks are inconclusive, which item 5 should report. |
| 25 | Business tables | Iceberg `lake.ofb`: bronze (`exchanges`, `contract_results`), silver (`consent_reads`, `balances`, `listing_pages`, `listing_items`), gold (`business_checks` with `pass`/`finding`/`inconclusive`), partitioned by `run_id`, `overwritePartitions` | Reruns replace their partition. The silver tables serve the later items. A single findings table was the alternative. Recording passes and inconclusive checks gives item 5 the denominators. |
| 26 | Business job tests | pytest with a local PySpark 3.5.9 on Python 3.10 (the image's), over runs exported in process by the validator's harness; plus an in-cluster smoke that compares the checks with the labels | Fast feedback without a cluster. The transmitter, proxy and validator need Python 3.13, so they export the runs as files rather than sharing one environment. Testing only in the cluster was the alternative. |
| 27 | Detection report | PySpark job (`jobs/report`) over the Iceberg tables and the labels (kept as bronze `labels`); gold `detection_*` tables partitioned by report name, plus Markdown in `s3a://lakehouse/reports/` | Same platform as item 4, and the history of reports can be queried. A standalone script was the alternative: no history. So were SQL views over Iceberg: hard to test, no readable report. See [report.md](report.md). |
| 28 | Metrics | The unit is the exchange. Recall per class, strict (inconclusive = missed) and conditional (over conclusive); precision per rule against its target classes and per layer; class × rule matrix; 95 % Wilson intervals | Precision per class is undefined when a rule serves two classes (`schema.body`). Strict and conditional recall separate the cost of the gating from the quality of the rules. With 1 to 10 positives per class, a bare percentage would mislead. |
| 29 | Volume | Campaigns: `make campaign` runs one validation per defect seed with more customers and reports them together; CI keeps one small run. The walk also fetches each history in one page of 1000 | More data where it matters (the committed report) without slowing CI. The single-page history cut the inconclusive balances from 7 of 9 to 3 of 9. |
| 30 | Gate | The report fails on the catalogue's invariants (precision 1 in both layers, conditional recall 1, no inconclusive contract check); strict business recall is reported, not gated. It replaces the business job's `--verify-labels` | One place compares with the ground truth. Strict recall varies with the seed and the day, so a threshold on it would be flaky. |
| 31 | More positives for the rare classes | The transmitter seeds the non-happy consents (expired, revoked, without balances, awaiting) for every customer, and the walk uses them on the accounts list and every balance. Per customer, `BALANCE_CONSENTS` (2) new consents read every balance again. The balance rule takes the account's history from any consent of the walk | In v1.0.0's reference campaign, `consent-not-enforced` had 3 positives and `inconsistent-balance` 10. Repeating a request does not help, because the draw depends on the request. A focused campaign with boosted rates was the alternative; it is left for later, as a separate report. The proxy needs no change. |
| 32 | Path dependencies between services | `editable = true` for the transmitter and the proxy in the test environments of the proxy and the validator | A non-editable path dependency is built once and is not rebuilt when its code changes, so local tests can run against stale code. CI always starts from a fresh environment. |
| 33 | Second source of consent state | The walk reads each consent twice before using it, the second time with a renewed client-credentials token (`CLIENT_TOKEN_RENEWED`). The business rule is unchanged: it takes the last read that passed the contract layer | In v1.1.0's reference campaign, 81 of the 661 `consent-not-enforced` positives were inconclusive because the only read had failed the contract layer. A plain repeat gets the same draw (decision 17), and the bearer is part of the key. Varying the query would add a parameter the spec does not declare. Using the creation and revocation responses was the alternative, but they also pass through the proxy, and the creation answers `AWAITING_AUTHORISATION` before the authorisation. |
| 34 | Spark image step in CI (backlog item 8) | `ADD --chmod=644` for the jars instead of a later `RUN chmod`, and `kind load` into the worker only (`KIND_LOAD`) for every image. No Docker layer cache, no jar cache | Measured on CI run 45274873024: the 78 seconds were about 15 to pull the base image, 3 to download the jars, 4 for the chmod and export, and 56 for `kind load` into two nodes. The chmod copied the jars into a second layer (400 MB, image 3.4 GB to 2.6 GB without it). The control plane is tainted `NoSchedule`, so loading it is wasted. Locally, `kind load` went from 80 to 43 seconds. A layer cache (buildx with the GitHub Actions cache) or a jar cache (`actions/cache`) would save the 3 seconds of downloads. A jar cache would also have avoided the failed first attempt of run 45274873024, when Maven Central answered every jar with one body. That was a one-off, and the checksums caught it; the cache can come back if it repeats. |
| 35 | Memory of the detection report | `memoryOverhead: 768m` for the report's driver and executor (default 384m); heap unchanged at 1g | One executor was OOMKilled in the reference campaign of 2026-11-23: the kernel kills the pod when heap plus off-heap (S3A and Parquet buffers, threads, metaspace) passes the limit, so it depends on how far the heap has grown. Measured on the campaign's three runs (cgroup `memory.peak`), the executor peaked at 1051 MiB of 1433 MiB; with 768m, at 981 MiB of 1792 MiB, and the report was the same. A larger heap was the alternative, but the heap was not what ran out. The business-rules job reads one run at a time and was left as it is. |
| 36 | Jars of the Spark image (revises 34) | `make jars` (`scripts/fetch-jars.sh`) downloads them into `.cache/jars/`, checked against `images/spark/jars.sha256`: Maven Central first, then its Google Cloud Storage mirror, up to 3 rounds, each wrong answer described in the log. The Dockerfile copies them (`COPY --chmod=644`); CI caches the directory, keyed on the sums file | Decision 34 left the jar cache out unless the failure of run 45274873024 repeated. It did, twice in the next hour: the first attempt of PR #12's run and the main run 45285785089, both with one body (`sha256:f95609e6…`) for every jar. With a cache hit, CI does not reach Maven Central; on a miss, the mirror and the retries cover a bad answer. The sum decides wherever the bytes came from, so the mirror adds no trust. Buildx with the GitHub Actions layer cache was the alternative: a second builder, and it still downloads on every key change. The other downloads of the Makefile (tools, specs) retry too (`CURL`, `--retry-all-errors`), after a 503 from raw.githubusercontent.com failed the specs step of a CI run on 2026-11-24. |
| 37 | Focused campaign (backlog item 9) | `make focused-campaign`: `scripts/campaign.sh` with rates for every run (the proxy's `DEFECT_RATES`, restored at the end). `FOCUSED_RATES`: contract classes 0, `inconsistent-balance` 0.4, `broken-pagination` 0.3, `consent-not-enforced` 0.2, `transaction-outside-window` 0.1. Reported apart, in [focused-report.md](focused-report.md). The business-rules job gets 768m of memory overhead, as the report did (decision 35) | The reference campaign measured some rules on few cases (`pagination.total-records` 10, `balance.matches-transactions` 35). With the contract classes off, nothing is excluded by the gating, so the rules are measured on their own. The rates add up to 1, the most one draw allows. The mix is artificial, so it does not replace the reference figures. Keeping the contract rates at their defaults was the alternative: the gating would hide part of the boosted cases. In the first focused campaign the business-rules executors were OOMKilled in two runs (Spark retried); a rerun peaked at 1311 MiB of 1433 MiB, and at 1273 MiB of 1792 MiB with the overhead, with the same report. |
| 38 | Consent renewal (backlog item 11, renewals only) | The transmitter implements `POST /consents/{id}/extends` and `GET /consents/{id}/extensions` (bearer: the consent; 422 for a consent not `AUTHORISED` or an earlier date). Per customer the walk renews a consent twice, reads its history with each client token and the consent twice, and makes two renewals that must be refused. Two business classes, appended to the catalogue at 0.05: `broken-extension-history` and `extension-not-reflected`, with the rules `extensions.history-consistent` and `consent.extension-reflected` | The renewal is the part of the consent state machine the walk could exercise with the dataset as it is. Multiple approvers (`DEPENDE_MULTIPLA_ALCADA`) and the permission-group rules need business customers and an approval model, so they are left for a later release. The read rule compares with the walk's own request body, not with the 201's: the request is the receiver's own record. When the 201 failed the contract layer, the renewal may not have taken effect, so what follows it is inconclusive. Appending the classes keeps the other classes' draws as they were (decision 17); the default rates add up to 0.95. The proxy asks the transmitter for the history to know the date a stale read would show. The focused rates are rebalanced to make room for them. The jobs' tests now export eight runs, and their local Spark driver gets 2g of heap: with the default 1g, `test_several_runs_add_up` ran out of memory on the main CI run 45298255333. |
| 39 | Operational requirements (backlog item 13) | `specs/operational/requirements.json`: our own transcription of the numbers, each block citing a source with its version; where sources disagree, the case and the reading chosen are in the file. `extends` and `extensions` follow the portal (`baixa`, 4000 ms), not the manual (`alta`). `scripts/check-requirements.py` runs in the validator's environment (PyYAML) | The portal publishes these numbers as web pages, which change without a commit to pin: only the version number and the date identify what was read. JSON needs no dependency in the Spark job that will read it. The manual's worked examples are the test vectors of the rules, and each check must notice a broken copy, as the `ofb-*` rules must fire on the fixture (decision 12). Following the manual for the renewals was the alternative; the portal's value is the one given per endpoint. |
| 40 | Design of the operational layer (items 13 to 18) | Live telemetry plus a seeded 90-day history of reports, instead of a faster clock. Detection is measured per endpoint and day for response time and availability, and per test case for limits. v1.4.0 measures; v1.5.0 adds limits, driven by k6 (v2.3.0, the newest v2 release at least two weeks old) | A faster clock would stop measuring real latency. The regulation judges days and months, so a per-request unit would measure something it does not. The limits need state in the transmitter, so they come apart. k6 is AGPL-3.0: it is used as a test tool, not modified or distributed. Locust (MIT) was the alternative. |
| 41 | Telemetry (backlog item 14) | One PCM report per exchange from each side: the validator (CLIENT, timed by the walk) and the proxy (SERVER, timed by an ASGI middleware around it), as JSONL in `s3://lakehouse/pcm/<side>/run=<id>/`, the report wrapped with the run and the time it was written. The PCM's OpenAPI file pinned by commit; `additionalInfo` and the domains from the portal's pages. `processTimespan` in whole milliseconds rounded up | The two sides measure different things and the regulation counts the client's, with the server's as fallback, so both are needed, and pairing them is how the PCM finds divergences. The middleware sees what the gateway would, the injection included; timing inside the route would miss the error responses and the body's sending. The report is kept as the PCM would receive it, so a line could be posted as it is. The file is older than the pages and has an invalid enum value (`'NO_CREDENTIAL, NONE'`), so it cannot be the reference for the domains; the tests list the disagreements the walk meets. Rounding down would report fast calls as 0, which the portal leaves out. Sending the reports to a mock PCM was the alternative: it would add a service and compute nothing the job will not. |
| 42 | History (backlog item 15) | `jobs/history`: a PySpark job over units (an endpoint on a day), each generated from the seed, the endpoint and the day. Six classes (`slow-day`, `outage`, `outage-chronic`, `overload`, `unpaired`, `inconsistent-pair`) and four edges at the thresholds; at most one episode per unit, the widest scope first. The labels are the units' ledgers: what was built, checked against the episode | The regulation's units are days and 90-day windows; a seeded generator gives them in a minute. Generating per unit makes the history parallel and a day independent of the run's length. Building each episode to a target (the time at the P95 rank, the failed minutes, the share of 529) makes the expected verdict known without a metric to compute it; the ledger only counts what was built, and the tests recount it from the reports. One episode per unit keeps each verdict tied to one cause. Drawing per request and labelling from a reading of the reports was the alternative: the labels would depend on a second implementation of the metrics. The executors run Python here, so the job ships its module with `addPyFile`: `deps.pyFiles` with `local://` reaches the driver only. |
| 43 | Operational job (backlog item 16) | `jobs/operational`: Spark DataFrames only. The reports are paired by `fapiInteractionId` and the five fields at 7 days (and at 08:00 for the reporting goal); the view is the client's report, the server's when the client's is missing. Six Iceberg tables: per endpoint, institution and API, per day and per month. P95 rank and the 90 % of days in integers, half up. `--check` compares every label of a history and fails on a difference; CI runs it | The PCM decides with both sides, so the job must pair before it measures; computing from one side would miss the unpaired and inconsistent ones the goals limit. A DataFrame window gives the P95 rank and the 90-day moving mean without Python on the executors. Integer rounding avoids a float that sits on .5. The monthly verdicts are not in the labels: the tests recompute them from the labelled days. Hand-built cases cover what the history does not reach (a rank that rounds, a month at 27 and 28 of 31 days, three late days); mutating the job showed the need for them, and for reports sent just before 08:00, now part of the history. |
| 44 | Operational detection report (backlog item 18) | Per verdict and per its own unit (endpoint-day, endpoint, API-day, institution-day, and the months): recall over the units with a target cause, precision with the causes the requirements allow (a 529 is an error in availability; a month's long availability looks back 90 days), the edges as the requirements say. Written by the operational job (`--report`) to `lake.ofb.operational_detection_*` and Markdown; gated in CI. The history's overloads come in one burst minute | The verdicts judge units, not exchanges, so the report of the other layers does not fit. Counting only targets as right would call the requirements' own consequences false positives; counting everything right would measure nothing, so the allowed causes are listed per verdict and the targets alone make positives. The report found that spreading the 529s one per minute saturated the long availability (11 of 11 endpoints flagged); a burst is also how an overload looks. A separate report job was the alternative: one more SparkApplication in CI for the same data. |
| 45 | Design of the limits (backlog item 17, v1.5.0) | The transmitter applies the traffic and monthly limits at the minimums (calendar minute; Brasília month; 2XX of first pages only), the origin from a stand-in header `x-mock-client-org-id`. Each walk is a receiver of its own (`uuid5` of the run id). The defects come from a second proxy (`proxy-limits`) with only the limit classes, drawn per test case (origin, endpoint, object), not per response. k6 drives one origin per test case; a PySpark job judges from the client's log alone: a 429 with fewer than the TPM in the 60 seconds before it, a 423 with fewer than the minimum of counted successes in the month, any 429 or 423 on Consents | The limits are minimums, so only a limit applied too early or where none applies is a defect. A fixed receiver would carry the monthly counts across the runs of a campaign (8 calls a month on most endpoints). A second proxy leaves the walk and its reports as they are and needs no rollout between steps. k6 repeats identical requests, so a draw per response would be all or nothing per key. The 60-second window accepts both a calendar and a sliding limiter (`tpm-window`) |
| 46 | The limits load (backlog item 17) | `infra/k6/limits.js`: one origin per test case, made from the case's name, so the proxy's draw depends on the seed only; each run restarts the transmitter and the limits proxy (both count from zero) and waits until their Services answer from the new pods. Traffic bursts from a minute boundary, all in parallel; monthly cases interleave pages and failing requests. The client's view is one `console.log` record per request in k6's JSON log, uploaded by the validator's image to `limits/client/run=<id>/`. k6 2.3.0 by digest from Docker Hub | Measured in kind: 400 requests per second of 200s through the proxy and the transmitter, p95 under 8 ms, so the six bursts (about 10,800 requests) fit in one minute (8 to 20 seconds). k6's metrics output writes about 14 points per request (some 80 MB a run); the records are what the judge needs. Origins per run would make the CI's draws change from run to run. kind cannot load the multi-platform k6 image (`ctr: content digest ... not found`). 2.4.0 was not yet two weeks old when chosen |
| 47 | The limits job and its report (backlog item 17) | `jobs/limits`: each request matched to its endpoint of the requirements by method and path; a 429 is early with fewer than the TPM requests of the origin to the endpoint in the 60 seconds before it, a 423 with fewer than the minimum of 2XX first pages of the origin, endpoint and object in the Brasília month before it, any 429 or 423 on Consents. The report's unit is the test case; its causes are the labelled limit classes, or the edges the load builds in the clean cases (`tpm-at-limit`, `monthly-at-limit`: not flagged). The operational report's summary and gate, given this job's verdicts; `early-traffic-limit` is also allowed for an early 423. Gated in CI over the seed-42 run | The judge must not see the labels, or it would measure the proxy rather than find the defects; the endpoints come from the requirements so a new endpoint needs no code. The 60-second window passes a calendar and a sliding limiter (`tpm-window`). A test case is what the proxy draws, so a unit per request would weigh a burst of 1,000 refusals as 1,000 findings. The edges carry the exact-limit checks of `make limits-smoke` into the report. A 429 put in place of a counted success makes the transmitter's 423 look early to the client: the cause is the early 429, so it may explain the flag. Reusing `detection.py` keeps one definition of precision, recall and the gate |
